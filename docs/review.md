# コードレビューと修正内容

## 対応した問題

- WebSocket: `/ws/orders` の接続直後にJWTを検証し、認証成功後だけ注文配信の接続一覧へ追加するようにした。JWTはURLへ入れず、最初のWebSocketメッセージで送信する。
- 注文トランザクション: 注文と通知履歴を一括コミットし、DB処理中の例外ではロールバックするようにした。WebSocket・Web Pushの配信失敗は、保存済み注文をクライアントへ失敗として返さない。
- 数量: APIとDBの両方で `1 <= quantity < 20` を保証し、空の注文も拒否する。フロントの数量操作も19個を上限にした。
- 席セッション: 1席につき進行中セッションを1つにする部分一意制約を追加した。セッションと席状態を同じトランザクションで更新する。
- 無効メニュー: 非表示メニューIDを直接指定した注文を拒否するようにした。
- 入力検証: ユーザー、メニュー、席、備考などへ長さ・価格・パスワード長の制約を追加した。申請中IDの重複もDB制約で防ぐ。
- 席削除: 利用履歴がある席は削除せず、409を返すようにした。
- 注文一覧: 席ごとの繰り返しクエリを、JOINによる一括取得へ変更した。
- メニュー更新: カテゴリ変更が保存されない不具合を修正した。
- マイグレーション: `backend/migrations/003_add_integrity_constraints.sql` に数量、進行中席セッション、申請中IDの制約を追加した。

## 運用上の注意

- `003_add_integrity_constraints.sql` はデプロイ前に適用する。既存データに数量範囲外、または同じ席の進行中セッション重複がある場合は、先にデータを確認・修正する。
- WebSocketの接続一覧はプロセス内にあるため、複数ワーカーで完全なリアルタイム配信を行うにはRedis等の共有ブローカーが必要。現在の3秒ポーリングにより最終的な一覧同期は行われる。
- 公開登録・ログインのレート制限は、複数ワーカーでも一貫して制限できるリバースプロキシまたは共有ストア側で設定する。
